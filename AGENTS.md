# AGENTS.md

## Про проєкт

Це чинний сайт Дмитрушківського ліцею, а не новий проєкт. Зберігайте поточну архітектуру, структуру сторінок, наявні функції та реальний контент. Не перебудовуйте сайт з нуля.

Поточний візуальний напрям — сучасний **Premium School**: темно-синя база, стримані золоті акценти та висока читабельність. Нові або змінені елементи мають узгоджуватися з цим стилем.

## Обов'язкові правила

- Використовуйте лише наявний реальний контент. Не вигадуйте сторінки, новини, документи, контакти, фотографії, підписи, факти чи інші дані.
- Не видаляйте наявні сторінки, функції або дані без прямої команди користувача.
- Не змінюйте Firebase, Firestore, Authentication, `firestore.rules`, форму звернень або адмін-панель без прямої потреби конкретного завдання.
- Ніколи не послаблюйте Firestore rules до публічного `read`/`write`.
- Firebase має залишатися на безкоштовному тарифі Spark. Не підключайте платні сервіси, білінг або ресурси без прямої команди користувача.
- Не створюйте, не вставляйте у файли та не показуйте в повідомленнях секрети, токени, паролі, приватні ключі або інші облікові дані.
- Не переписуйте справні файли лише заради рефакторингу, форматування чи зміни стилю коду. Віддавайте перевагу мінімальним, локальним і безпечним змінам.
- Для локального бага спочатку визначте мінімальний набір релевантних файлів. Не проводьте повний аудит усього репозиторію, якщо цього не потребує завдання.
- Не робіть commit, push, merge, deploy і не змінюйте гілку `main` без прямої команди користувача.

## Адаптивність і візуальна якість

- Працюйте за принципом mobile-first.
- Для змін інтерфейсу перевіряйте щонайменше ширини `320px`, `390px`, `768px` і desktop.
- Не допускайте horizontal overflow, перекриття, виходу за межі контейнерів, недоступних елементів керування або обрізання тексту й інтерактивних елементів.
- Зберігайте читабельність, контраст, зрозумілу ієрархію та коректну роботу клавіатури/фокусу там, де це стосується зміни.

## Перевірки

- Після змін JavaScript виконуйте синтаксичну перевірку всіх змінених JS-файлів.
- Після суттєвих змін використовуйте релевантні наявні перевірки: `tools/repair/quick_check.py`, `tools/test/e2e.py` та/або `tools/test/browser_test.py`.
- Обирайте перевірки пропорційно ризику. Не запускайте дорогі, довгі або повні перевірки для малої локальної зміни без потреби.
- Сторонні помилки або попередження від iframe, Google чи Facebook не вважайте помилками власного JavaScript, якщо вони не спричинені зміною і не впливають на функціональність сайту.
- Не повторюйте вже успішні перевірки без нової причини або змін, які можуть вплинути на їх результат.

## Економне використання агентних лімітів

- Не перечитуйте великі файли повністю, якщо достатньо пошуку, списку збігів або конкретного фрагмента.
- Спочатку використовуйте пошук за назвою, селектором, функцією чи текстом, а потім відкривайте лише релевантні ділянки.
- Групуйте пов'язані читання та перевірки, коли це безпечно й доречно.
- Не повторюйте вже виконаний аналіз і не запускайте повторно успішні перевірки без причини.
- Не просіть підтвердження для звичайного безпечного читання, пошуку або діагностики в межах проєкту.
- Зупиняйтеся після виконання конкретного завдання; не розширюйте обсяг роботи самостійно.

## Рекомендований workflow

1. Зрозуміти конкретне завдання та його межі.
2. Знайти мінімальний набір релевантних файлів і фрагментів.
3. Внести мінімальну безпечну зміну, не зачіпаючи сторонню функціональність.
4. Виконати релевантну перевірку, пропорційну ризику зміни.
5. Зупинитися й коротко доповісти результат. Не виконувати push або deploy.

- результат кожної перевірки.
